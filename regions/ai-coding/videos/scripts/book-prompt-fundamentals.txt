=== title
heading: Prompt 的基本功
sub: 把它當成寫需求：越具體、越能被驗證，結果越穩
> 這一章是提示詞的基本功。對有經驗的工程師來說，最好的理解方式，是把它當成寫需求：越具體、越能被驗證，結果越穩。

=== code
heading: 含糊與具體
```text
# 含糊
修好這段程式。

# 具體
我在除錯一個計算折扣的 Python 函式。傳入負值時會丟出
ValueError: Discount cannot be negative。程式碼如下：<code>

請依序：1) 指出 bug  2) 說明為什麼會發生
       3) 提供加入輸入驗證的版本  4) 附上測試案例
```
> 先看一個對比。含糊的版本只有一句：修好這段程式。具體的版本會說明背景，附上實際的錯誤訊息與程式碼，並且依序列出要的產出：指出錯誤、說明原因、提供加入輸入驗證的版本、附上測試案例。這就是把提示詞當成寫需求：要的產出一項一項列清楚，每一項都能被驗證。

=== figure
heading: 一個結構化提示詞的組成
src: prompt-anatomy.svg
caption: 驗收標準最好由程式去檢查，而不是只寫在提示詞裡
> 一個提示詞的要素可以歸納成三個：情境，包括背景、限制與技術需求；指示，簡單直接、拆成步驟；範例，示範想要的輸入輸出格式與邊界。圖上還有一個重點：驗收標準最好由程式去檢查，而不是只寫在提示詞裡。

=== table
heading: 六種基本類型
| 類型 | 做法 | 適合 |
| zero-shot | 不給範例，直接要求 | 簡單、常見的任務 |
| few-shot | 先給幾個範例再提問 | 要固定風格或格式 |
| open-ended | 開放式問題 | 找想法、討論取捨 |
| constrained | 限定範圍與條件 | 已知要什麼、要精準 |
| structured | 指定章節或格式 | 文件、報告 |
| iterative | 對話式反覆修正 | 一開始講不清楚時 |
> 提示詞有六種基本類型。零範例：不給範例，直接要求，適合簡單常見的任務。少量範例：先給幾個範例再提問，適合要固定風格或格式的時候。開放式：用來找想法、討論取捨。限制式：限定範圍與條件，適合已經知道要什麼、要求精準的時候。結構式：指定章節或格式，適合文件與報告。反覆式：用對話一步步修正，適合一開始講不清楚的時候。
> 少量範例的一個例子：先貼兩個符合你風格的小函式，例如加法與限制範圍，再要它照同樣的風格，寫一個計算階乘的函式。範例同時傳達了命名、長度與註解風格，這比用文字描述更有效。

=== bullets
heading: 兩個要記住的限制
- 限制式與結構式提示詞，都不保證模型會照做
- 「讓模型先問澄清問題」很有用，但「大多數情況會更好」通常沒有實驗
- 算術例子：234 × 432 ＝ 101,088；換了問法仍可能偶爾算錯
> 有兩個限制要記住。第一，限制式與結構式的提示詞，都不保證模型會照做，因為輸出仍然是機率性的。第二，一個常見的建議是讓模型先對你的提示詞提出澄清問題，再幫你改寫。這很有用，但「大多數情況下會更好」這類說法，通常沒有附上實驗，應當視為經驗談。
> 再看一個算術的例子：兩百三十四乘以四百三十二，正確答案是十萬一千零八十八。直接問可能算錯，改成「用三種方法計算並展示過程」可能就答對；但同樣的提示詞重跑幾次，仍然可能出錯，因為大型語言模型並不是為了精確計算而設計的。

=== bullets
heading: 進階觀點
- 提示詞是程式碼：版本控制、審查、用評測比較兩個版本
- 「展示推導過程」的效果要自己量
- 精確計算交給工具：算術、日期、單位換算、大量資料
- 重要的格式用結構化輸出加 schema 驗證
> 進階觀點有四個。提示詞是程式碼，要版本控制、要審查、要用評測比較兩個版本是不是真的有差。「展示推導過程」的效果要自己量：它對某些任務有幫助；但對已經具備推理能力的現代模型，是否還需要明說，取決於模型與任務，要用評測決定，而不是迷信。精確的計算，例如算術、日期、單位換算、大量資料處理，要交給工具執行，這也是工具使用存在的動機。重要的格式，要用結構化輸出加上結構定義的驗證，不要只靠提示詞裡的一句話。限制不保證被遵守，本身就是一個設計約束。

=== quiz
heading: 檢查點
q: 針對 234 × 432，反覆提示「請一步一步算」仍然偶爾出錯。工程上最穩的處理方式是？
- 把 temperature 調到最高
- 加上角色扮演，例如「你是數學教授」
- * 提供計算工具，讓模型呼叫工具取得精確結果，並驗證工具的輸出
- 把 prompt 寫得更長
> 檢查點：反覆要求一步一步算，仍然偶爾出錯，最穩的做法是什麼？答案是第三個：提供計算工具，例如讓它執行程式碼，並驗證工具的輸出。模型只負責決定要算什麼、怎麼使用結果，精確的計算交給確定性的工具，可靠性才會從看運氣，變成可以驗證。

=== end
heading: 重點回顧
- 提示詞三要素：情境、指示、範例
- 六種基本類型，各有適合的場景
- 限制不保證會被遵守：用程式驗證
- 精確計算交給工具
> 回顧一下。提示詞的三要素是情境、指示與範例；六種基本類型各有適合的場景；限制不保證會被遵守，所以要用程式驗證；精確的計算交給工具。
> 思考練習會問你：怎麼證明某次提示詞修改真的比較好，而不是剛好這一次運氣好？提示是：建立一組有代表性的任務與自動評分的方式；新舊版本在同一組任務上各跑多次，報告通過率與信賴區間，而不是單次結果；同時也要看成本與延遲，因為更長的提示詞可能提高成本；並且看失敗案例的分類，確認沒有引入新的退步。
