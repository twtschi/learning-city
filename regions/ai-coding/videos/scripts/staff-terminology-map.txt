=== title
heading: 術語地圖：把容易混淆的詞分開
sub: 拆錯詞，修法就會選錯
> 這一章是一張術語地圖。目標不是背定義，而是在討論的時候，能把容易混在一起的詞拆開，因為拆錯了詞，修法就會選錯。我們從最實用的一張表開始。

=== table
heading: 同樣是「AI 錯了」，修法不一樣
| 症狀 | 比較可能的類別 | 該做的事 |
| 呼叫根本不存在的函式或套件 | 幻覺（編造） | 實際執行、型別檢查、依賴白名單 |
| 呼叫曾經存在、現已移除的 API | 過時 | 指定版本、提供對應版本的文件 |
| 語法正確，但違反專案慣例或內部 API | context 不足 | 規則檔、範例、相關檔案 |
| 只對常見情況正確 | 偏向常見模式 | 邊界測試、性質測試 |
| 需求含糊，模型選了一種解讀 | 規格問題 | 先釐清需求並寫成測試 |
> 同樣是 AI 錯了，修法不一樣。呼叫了根本不存在的函式或套件，是幻覺，也就是編造；修法是實際執行、型別檢查，以及依賴白名單。
> 呼叫了曾經存在、但已經移除的介面，是過時，因為訓練資料有截止日；修法是在上下文指定版本，並提供對應版本的文件。
> 語法正確、卻違反專案慣例或內部介面，是上下文不足；修法是規則檔、範例與相關檔案。只對常見情況正確，是偏向常見模式；修法是邊界測試與性質測試。而需求含糊、模型選了一種解讀，那是規格問題，不是模型問題，要先釐清需求，寫成測試。

=== bullets
heading: 模型與資料：三組要分清的詞
- Knowledge cutoff：訓練資料有截止日，不知道之後的新版本
- Representation gap：冷門語言與內部框架，模型知識薄弱
- Generalization gap：你的私有程式碼多半落在「沒見過」那一側
note: Context 不等於記憶：沒放進這次請求的東西，模型看不到
> 模型與資料這一區，有三組詞要分清。知識截止日，是訓練資料有截止日期，模型不知道之後的新版本與棄用。代表性缺口，是某些語言或函式庫在公開程式碼裡很少見，所以冷門語言、新框架、公司內部的專用語言，輸出要更嚴格驗證。泛化落差，是模型在訓練資料和沒見過的資料上表現的差距，而你的私有程式碼，多半落在沒見過的那一側。
> 還有一點：上下文不等於記憶，沒有放進這一次請求的東西，模型就看不到。

=== table
heading: 品質與測試：每一種都在回答不同的問題
| 術語 | 它回答的問題 |
| Regression test | 改動有沒有弄壞原本的行為？ |
| Characterization test | 沒有測試的舊程式，現在的行為是什麼？ |
| Differential test | 新舊兩版，對同一組輸入是否一致？ |
| Property-based test | 在大量輸入下，某個性質是否一直成立？ |
| Mutation testing | 程式被故意破壞時，測試會不會變紅？ |
> 品質與測試這一區，每一種測試都在回答不同的問題。迴歸測試問：這次改動有沒有弄壞原本的行為。特徵化測試問：一段沒有測試的舊程式，現在的行為到底是什麼，先記錄下來再動手。差分測試問：新舊兩個版本，對同一組輸入是否一致。性質測試問：在大量自動產生的輸入下，某個性質是否一直成立。突變測試則問：程式被故意破壞的時候，測試會不會變紅，用來檢查測試本身的強度。

=== big
heading: 最常被忽略的一個詞
text: Oracle：能判定輸出對不對的依據
note: 規格、參考實作、舊系統、人。沒有便宜的 oracle，就不該提高 AI 的自主程度
> 這一區最常被忽略的詞，是判定依據。它是能判斷輸出對不對的東西：規格、參考實作、舊系統，或是人。一個很實用的原則是：沒有便宜的判定依據，就不該提高 AI 的自主程度。

=== bullets
heading: 重構、法務與交付
- Refactoring：不加功能、不修錯誤；「行為不變」是定義的一部分
- Fair use 不是「合法」的同義詞；copyleft 不是所有開源授權都有
- Indemnification 有條件；CWE 是弱點型態，不等於可被利用的漏洞
- Code review：AI 可以先篩一輪，但責任與核准仍在人
> 其他幾區也有容易混淆的詞。重構的定義是不加功能、不修錯誤，所以「行為不變」是定義的一部分，需要判定依據來證明。法務方面，合理使用不是合法的同義詞，而是還沒有定論的抗辯理由；著佐權條款也不是所有開源授權都有。供應商的賠償承諾是有條件的；弱點分類描述的是弱點型態，不等於可被利用的漏洞。交付方面，AI 可以先幫忙審查一輪，但責任與核准仍然在人身上。

=== quiz
heading: 檢查點
q: Python 3.12 的專案裡，AI 建議了一個在 3.12 已被移除的標準庫函式。最準確的分類與第一個修法？
- 這是幻覺，應該要求模型「不要編造」
- * 比較接近過時：在 context 指定版本並提供對應文件，再用測試與實際執行驗證
- 這是偏見，應該更換訓練資料
- 這是規格問題，應該重寫需求
> 檢查點：在三點一二版的專案裡，AI 建議了一個在這個版本已經被移除的標準函式，該怎麼分類？答案是第二個，比較接近過時。這個函式曾經存在，問題是模型的知識停在舊版本。把它叫做幻覺，就會把力氣花在叫模型別亂講，而不是補上版本與文件這種真正有效的上下文。

=== end
heading: 怎麼用這張地圖
- 遇到「AI 寫錯了」，先分類再決定修法
- 討論品質時，先問 oracle 是什麼
- 看到生產力數字，先問它屬於哪一種證據
> 最後，怎麼用這張地圖？遇到 AI 寫錯了的回報，先分類，再決定修法；討論品質時，先問判定依據是什麼；看到生產力的數字，先問它屬於哪一種證據，這會在第八週詳細討論。
> 思考練習會請你向產品經理解釋：幻覺和過時，為什麼是兩件事，處理方式又有什麼不同。
