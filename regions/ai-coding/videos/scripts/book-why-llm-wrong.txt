=== title
heading: 為什麼 AI 會寫出「看起來對」的錯誤
sub: 預測不是查證：錯誤從哪裡來，又該怎麼攔住
> 這一章回答一個每個使用 AI 寫程式的人都會遇到的問題：為什麼 AI 會寫出看起來很專業、實際上卻是錯的程式碼？答案藏在模型的運作方式裡。

=== figure
heading: 核心觀念：預測，不是查詢
src: next-token.svg
caption: 每一步只預測最可能的下一個 token，沒有任何一步在查證事實
> 常見的比喻是句子接龍。看到「貓坐在」，你會很自然地想到「墊子」，而不是去查一張表。模型做的事類似，只是規模大得多：根據目前的輸入，以及已經生成的內容，預測最可能的下一段文字。
> 所以，最可能的延續，不一定是正確的答案。當訓練資料裡某種錯誤寫法很常見，或者你的問題本身含糊，模型會同樣自信地輸出錯誤的內容。它沒有一個可以對照事實的真相資料庫。

=== code
heading: 生成迴圈裡，沒有任何一行在驗證
```cpp
std::vector<int> ctx = tokenize(prompt);
while (!is_eos(ctx.back()) && ctx.size() < max_len) {
    std::vector<float> logits = model.forward(ctx);
    int next = sample(logits, temperature, top_p);
    ctx.push_back(next);
}
```
note: 驗證必須由迴圈之外的系統負責
> 用工程師熟悉的方式看，核心迴圈大致是這樣：把提示詞切成詞元，然後反覆執行：模型算出分數，取樣器選出下一個詞元，接回上下文，再來一輪。
> 請注意，迴圈裡沒有任何一行是在驗證這個詞元對不對。驗證，必須由迴圈之外的系統負責。

=== steps
heading: 三類成因
- 模型不是資料庫：用機率生成新文字，同一個問題可能有不同答案
- 訓練階段的問題：把資料都當成同等有效，偏好常見但次優的寫法
- 誤解 context：變數名多義、函式重載、需求含糊
> 錯誤的成因可以分成三類。第一，模型不是資料庫。資料庫回傳你存進去的東西，模型則是用機率生成新文字，所以同一個問題可能得到不同答案，也可能組合出從沒見過的內容。
> 第二，訓練階段的問題。模型把訓練資料都當成同等有效，無法自己判斷對錯，於是會偏好常見但次優的寫法、過度依賴熱門套件、只對常見情況正確，或複製過時的寫法。
> 第三，誤解 context。變數名稱有多重意義、函式重載、介面呼叫合法但不適用、語法正確卻違反慣例，或是需求本身就含糊。

=== code
heading: 典型錯誤：能跑，但次優
```python
# 常見但次優：list 的 in 是線性掃描，整體 O(n^2)
seen = []
for x in items:
    if x not in seen:
        seen.append(x)

# 保留順序的去重
unique = list(dict.fromkeys(items))
```
> 「能跑但次優」是很典型的錯誤，因為這種寫法在訓練資料裡非常常見。例如用串列來去除重複：每次檢查是否已經出現過，都是線性掃描，整體是平方的複雜度。
> 懂行的人會改用字典或集合。兩段程式都正確，測試也都會過，差別只在資料量變大的時候。這類問題，要靠專業判斷與效能測試才抓得到。

=== bullets
heading: 緩解方式與要校正的說法
- 提供規格與限制、附上相關程式碼、講清楚錯誤處理與輸入輸出
- 把複雜功能拆成小而聚焦的部分
- 「它會從每次接受的建議中即時學習」不該當成事實
- 「節省三成時間」這類數字多半是個人經驗，不是對照實驗
> 緩解的方式包括：提供詳細的規格與限制，附上相關的程式碼，講清楚錯誤處理與預期的輸入輸出，並把複雜的功能拆小。
> 也有幾個常見說法要校正。第一，「它會從我每次接受的建議中即時學習」不該當成事實；已部署模型的權重，不會因為你按一次接受就改變。想穩定提升風格的一致性，要用規則檔和範例當作上下文。第二，「節省三成時間」這類數字，多半是個人經驗，不是對照實驗。

=== quiz
heading: 檢查點
q: 同事說：「Copilot 會從我每次接受的建議中即時學習。」哪個回應最準確？
- 完全正確，權重會在每次接受時更新
- * 不該當成事實；要穩定提升風格一致性，應提供規則檔與範例作為 context
- 完全錯誤，模型從不使用使用者回饋
- 只有開源模型才會即時學習
> 檢查點：同事說程式助手會從他每次接受的建議中即時學習，哪個回應最準確？答案是第二個。這個說法過度簡化，回饋如何被使用要看供應商的政策；真正可控、可驗證的做法，是把團隊慣例寫進規則檔與範例，每次都放進上下文。

=== end
heading: 重點回顧
- 模型預測最可能的延續，不查證事實
- 錯誤會被寫得很自信，所以「看起來對」沒有意義
- 把「看起來對」變成可執行的檢查：型別、測試、風格檢查、實際執行
> 回顧一下。模型預測的是最可能的延續，不會查證事實，所以錯誤也會被寫得很自信。最重要的結論是：把「看起來對」，變成可以執行的檢查，例如型別檢查、單元測試、風格檢查，以及實際跑一次。
