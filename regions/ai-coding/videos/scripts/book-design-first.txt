=== title
heading: 先設計再生成
sub: 從「要解決什麼問題」到可以執行的骨架
> 這一章談一個很容易被跳過的步驟：先設計，再生成。我們用一個業餘無線電執照模擬考網站當例子，看看在寫程式之前，怎麼先用 AI 把設計與需求弄清楚。

=== bullets
heading: 第一步不是開 IDE
- 先問：到底要解決什麼問題？
- 讓 AI 幫你找盲點：這類應用常見的邊界情況有哪些？
- 這個領域有哪些法規考量？通常重視哪些非功能需求？
> 第一步不是打開開發環境，而是問：到底要解決什麼問題？接著讓 AI 幫你找盲點，例如：這類應用常見的邊界情況有哪些？這個領域有哪些法規考量？這類應用通常重視哪些非功能需求？

=== code
heading: 起手式提示詞的五個部分
```text
你是一位有十五年經驗的軟體架構師。                  # 角色
任務：幫我拆解下面的問題，找出盲點。                # 任務
背景：Python 網站，要從題庫隨機抽 35 題做模擬考。   # 背景
指示：列出邊界情況、非功能需求與可能的陷阱。        # 指示
輸出：編號清單，每項附一行理由。                    # 結尾（格式）
```
> 一個起手式的提示詞，可以拆成五個部分：角色、任務、背景資訊、指示，以及結尾，也就是指定輸出格式。角色寫得越具體越好，例如有十五年可擴展系統經驗的架構師。套用到這個案例，就是請它拆解問題、找出盲點，背景是一個要從題庫隨機抽三十五題的網站；指示是列出邊界情況、非功能需求與可能的陷阱；輸出是附理由的編號清單。

=== figure
heading: 流程：設計文件、需求、使用者故事、骨架
src: design-flow.svg
caption: AI 起草，人守住每一個關卡
> 接下來的流程是：讓 AI 產出設計文件的初稿，從設計文件擷取需求，再整理成使用者故事，最後建立程式的骨架。
> 最大的好處是不用從空白頁開始，工作從創作變成審稿。有人分享，設計會議的時間因此大幅減少；不過這是經驗談，不是實驗結果。但圖上紅色的部分是人的關卡，不能省：確認取捨、詢問利害關係人、確認骨架先能跑、驗收測試通過。
> 以模擬考網站為例，一條需求可能是：每場考試從題庫隨機抽三十五題，同一場不得重複。這句話可以直接寫成一個驗收測試：抽三十五題、檢查數量、檢查沒有重複。需求寫到能變成測試，才算寫清楚。

=== code
heading: Stub：先讓骨架能跑
```cpp
class QuestionSelector {
 public:
  // TODO(req 2.1): 從題庫隨機抽 n 題，同一場不得重複
  std::vector<Question> Select(int n) {
    return {};  // stub：先回空，讓呼叫端與測試可以先寫
  }
};
```
note: 用 TODO 標明意圖；骨架先能跑；不為還不需要的功能建 stub
> 骨架的做法叫做替身：先建立應用的結構，用簡化的替身函式代替真正的實作。要點有三個：用待辦註解標明每個替身的意圖；骨架要先能跑，再加功能；不要為還不需要的功能建替身。
> 以畫面上的程式為例，題目選擇器的介面先定下來，抽題函式暫時回傳空的結果。這樣呼叫端與測試可以先寫，實作之後再補。
> 好處是早期整合、早期發現不相容，以及更快的迭代。

=== bullets
heading: 交叉比對兩個模型
- 讓兩個模型各自從同一份設計文件擷取需求
- 結果有時很像、有時差很多
- 一致不等於正確：模型可能共享相似的訓練偏差
- 真正的驗證：回到利害關係人，並轉成可執行的驗收條件
> 一個便宜的覆核方法，是讓兩個不同的模型，各自從同一份設計文件擷取需求。結果有時很像、有時差很多，兩種情況都不要意外。
> 但要記得：兩個模型一致，不等於正確。它們可能共享類似的訓練偏差，一致只代表常見。交叉比對能找到遺漏，不能證明正確。真正的驗證，是回到利害關係人確認，並把需求轉成可以執行的驗收條件。

=== quiz
heading: 檢查點
q: 兩個不同的模型從同一份設計文件擷取出幾乎相同的需求清單。這能證明需求正確嗎？
- 能，兩個獨立來源一致就可以視為正確
- 能，因為這些模型都經過安全訓練
- * 不能；一致只代表「常見」，仍須向利害關係人確認並轉成驗收條件
- 不能，因為模型無法閱讀設計文件
> 檢查點：兩個模型擷取出幾乎相同的需求，能證明需求正確嗎？答案是第三個，不能。交叉比對能抓到單一模型的遺漏，但無法取代對真實需求的確認。把需求寫成可以執行的測試，才是可以重複驗證的證據。

=== end
heading: 重點回顧
- 先問問題，再找盲點
- 提示詞五部分：角色、任務、背景、指示、格式
- 設計文件由 AI 起草，決策與取捨由人簽名
- 先寫驗收測試，再讓代理程式實作
> 回顧一下。先問要解決什麼問題，再找盲點；提示詞可以拆成角色、任務、背景、指示與格式；設計文件可以由 AI 起草，但決策與取捨要由人簽名。技術選型的理由，也應該寫進設計文件，之後才有辦法被檢討。
> 對代理程式最可靠的工作流程之一，是先寫規格與驗收測試，再讓它實作，以測試通過作為完成條件。替身在這裡的角色，就是先把介面定下來，讓測試可以先寫。思考練習會請你描述，怎麼讓代理程式從規格一路做到驗收。
> 提示是：先和人一起把需求轉成驗收測試，包含邊界情況，讓測試一開始是紅的；再定義介面與替身，限制可以修改的目錄，設定最大步數與成本上限。架構決策、測試本身的修改，以及合併前的差異審查，都由人介入。最後，記錄每一次人工介入的原因，之後可以變成規則檔或評測的案例。
