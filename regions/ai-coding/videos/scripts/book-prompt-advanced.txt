=== title
heading: 進階 prompt 技巧
sub: 五種技巧，其實都在做同一件事
> 這一章介紹五種進階的提示詞技巧。它們看起來各有名字，其實都在做同一件事：給足上下文、把驗收標準寫進去、分步驟並且逐步檢查。最後我們會看到，這些技巧在代理程式的時代會怎麼變形。

=== steps
heading: 五種技巧
- 拆解推理：把大問題拆成小步驟，一步步問
- 遞迴精煉：每一階段的輸出，成為下一階段的輸入
- 預設環境：在開頭或系統訊息設定規則，讓回答一致
- 指示精煉：把含糊的需求寫成具體的步驟加限制
- 輸出控制：規定風格、長度、格式與允許的套件
> 第一種是拆解推理：把大問題拆成小步驟，一步步問。例如診斷容器裡的程式啟動失敗：先看容器狀態，再看日誌，再進到容器內檢查。建議的四步是：分解問題、設計每一步的提示詞、反覆評估、整合回饋，也可以讓不同的模型互相檢查。
> 第二種是遞迴精煉：每一階段的輸出成為下一階段的輸入，例如先做出階乘函式的基本版，再要求處理非整數與負數，最後再優化。第三種是預設環境：在開頭或系統訊息設定規則，讓回答保持一致。例如先宣告：你是一個 Python 助手，資料處理一律使用 pandas，除非特別指定，不要使用其他套件。第四種是指示精煉，第五種是輸出控制。
> 輸出控制，是規定風格、長度與格式，例如命名一律用小寫加底線，並限制不必要的套件匯入。

=== code
heading: 指示精煉的範例
```text
建立一個 Python 函式：
1. 參數為 JSON 檔路徑與資料庫連線字串
2. 驗證 JSON 含有必要欄位：user_id、timestamp、data
3. 轉換：timestamp 轉成 datetime、user_id 轉小寫
4. 以適當的 try/except 處理錯誤
5. 使用 SQLAlchemy 操作資料庫
6. 回傳 (是否成功, 處理筆數)
限制：參數與回傳值要有型別標註；用 logging 記錄錯誤；使用連線池。
```
> 指示精煉的意思，是把含糊的需求寫成具體的步驟加上限制。看這個例子：參數是什麼、要驗證哪些欄位、怎麼轉換、怎麼處理錯誤、用什麼套件操作資料庫、回傳什麼；最後再列出限制，例如型別標註、用日誌記錄錯誤、使用連線池。這份提示詞，幾乎就是一份可以直接轉成測試的規格。

=== bullets
heading: 給工程師的實用問法
- 要求取捨分析：比較幾個設計模式，再實作最佳選擇
- 要求複雜度分析：附上時間與空間複雜度
- 附上證據：效能剖析圖與查詢計畫，並給出目標數字
- 指定接手者：六個月後由另一個團隊維護
- 列出測試清單：負值、零、小數、最大整數、空值
> 還有一組給工程師的實用問法。要求取捨分析，例如比較幾個設計模式再實作最好的那一個；要求複雜度分析；附上證據，例如這個介面回應要兩秒，這是效能剖析圖和查詢計畫，請優化到兩百毫秒以內；指定接手者，例如假設六個月後由另一個團隊維護，請附上清楚的命名、日誌與監控；以及直接列出要測的情況：負值、零、小數、最大整數、空值。

=== code
heading: 把精煉變成有停止條件的流程
```python
def refine(task, max_rounds=5, budget_usd=1.0):
    draft = generate(task)
    for round_no in range(max_rounds):
        result = run_checks(draft)            # 測試、型別檢查、linter
        if result.passed:
            return draft                       # 停止條件：檢查通過
        if cost_so_far() > budget_usd:
            raise BudgetExceeded()             # 成本上限
        draft = revise(draft, result.failures) # 回饋具體的失敗
    raise GaveUp(draft)                        # 最大輪數：交給人
```
> 遞迴精煉如果沒有明確的停止條件，會變成無止境的來回。工程上的做法，是用客觀的訊號決定何時停止：每一輪先跑檢查，例如測試、型別檢查與風格檢查；通過就停止；超過成本上限就中止；沒通過，就把具體的失敗回饋給模型修改；超過最大輪數，就交給人。

=== bullets
heading: 在代理程式時代，原則不變
- 預設環境變成規則檔；指示精煉變成規格與驗收條件
- 拆解推理變成子任務拆分；輸出控制變成結構化輸出與驗證
- 「讓模型評審自己」有上限：能用客觀訊號，就不要只靠自評
- 終止條件、最大步數、成本上限是 harness 的責任
> 這些技巧在代理程式的時代會變形，但原則不變。預設環境變成規則檔；指示精煉變成規格與驗收條件；拆解推理變成子任務的拆分；輸出控制變成結構化輸出與 harness 層的驗證。
> 落實在 harness 裡，格式可以用結構化輸出加上 schema 驗證，不合格就帶著具體錯誤重試；風格交給 linter 與 formatter 自動檢查；範圍則限制可修改的目錄與指令，並檢查 diff 有沒有超出範圍。
> 還要記得兩件事：讓模型評審自己是有上限的，它和自己共享相同的盲點，能用測試與執行結果這類客觀訊號，就不要只靠自我評價。另外，終止條件、最大步數與成本上限，是 harness 的責任，不是提示詞的責任。

=== quiz
heading: 檢查點
q: 你要設計「產生、評審、修改」的自動精煉流程。最重要的設計決定是什麼？
- * 定義客觀的停止條件，並設定最大輪數與成本上限
- 讓模型自己決定「覺得夠好了」就停止
- 一律固定跑 10 輪，不管結果
- 每一輪都換更貴的模型
> 檢查點：設計自動精煉流程，最重要的決定是什麼？答案是第一個：定義客觀的停止條件，再用輪數與預算當保險絲。客觀的停止條件，例如測試通過或評分達標。沒有客觀訊號的精煉會一直改下去，成本與風險都不可控。

=== end
heading: 重點回顧
- 五種技巧的共同核心：context、驗收標準、分步檢查
- 精煉流程要有客觀的停止條件與預算
- 在代理程式裡，這些規則落實在 harness，而不只在提示詞
> 回顧一下。五種技巧的共同核心，是給足上下文、寫出驗收標準、分步驟檢查；精煉流程要有客觀的停止條件與預算；而在代理程式裡，這些規則要落實在 harness，而不只寫在提示詞裡。
> 思考練習會請你說明，輸出控制與指示精煉在 harness 裡要怎麼落實。
