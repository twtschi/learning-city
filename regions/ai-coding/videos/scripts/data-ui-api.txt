=== title
heading: 資料、前端與 API
sub: 請 AI 產生「能產生結果的東西」，並附上驗證方式
> 資料、前端與介面整合，是三類最常交給 AI 的日常工作。這一章把它們整理成一個共通原則：請 AI 產生能產生結果的東西，並且附上驗證方式，而不是直接產生結果本身。因為前者可以重複、可以審查，也可以驗證。

=== table
heading: 要產生器，不要產物
| 工作 | 直接要產物的問題 | 要產生器與驗證 |
| 範例資料 | 量大就省略、重複、不一致；無法重現 | 固定 seed 的產生腳本，加完整性檢查 |
| 格式轉換 | 手寫轉換容易在型別與跳脫出錯 | 用解析器與序列化器，做 round trip 比對 |
| Schema | 缺約束、缺索引、遷移不可逆 | 用清單審查，並在真實引擎上執行 |
| API 客戶端 | 只有成功路徑 | 在假伺服器上測失敗路徑 |
> 看這張表。範例資料如果直接要產物，數量一多就會省略、重複、不一致，也無法重現；比較好的是一支用固定種子產生資料的腳本，加上完整性檢查。格式轉換如果手寫，容易在型別與跳脫字元出錯；比較好的是用解析器與序列化器轉換，再做來回比對。結構定義要用清單審查，並在真實的資料庫引擎上執行。介面客戶端不能只有成功路徑，要在假伺服器上測試失敗路徑。

=== bullets
heading: Lab 1：範例資料用產生器
- 同一個 seed 得到同一份資料，換 seed 就不同
- 外鍵完整性由資料庫引擎強制：孤兒訂單被擋下
- CSV、XML、JSON 轉換後都要與原資料一致
- 電子郵件用保留網域，避免寫出真實地址
> 第一個實驗是範例資料產生器。只用標準函式庫：同一個種子得到同一份資料，換了種子就不同；外鍵的完整性由資料庫引擎強制，一筆指向不存在員工的孤兒訂單，會被直接擋下；轉成三種格式之後再轉回來，都要和原資料一致。電子郵件使用保留給測試的網域，避免寫出真實的地址。
> 實驗也提醒一件事：表格與標記語言格式轉回來時，數字欄位會變成字串，程式必須自己轉回來。AI 手寫的轉換常常漏掉這一步，而來回比對會直接指出來。

=== compare
heading: Lab 2：TOML 轉 YAML 的陷阱
col: 手寫的 YAML
- 國碼 `NO` 變成布林值 False
- 版本號 `1.10` 變成數字 1.1
- 與原始資料不一致
col: 用序列化器輸出
- 字串被正確加上引號
- 轉回來與原資料一致
- 結論：讓程式寫格式，不要讓模型手寫
> 第二個實驗是一個常見的需求：把一份設定檔從湯莫格式轉成雅莫格式。手寫轉換看起來無害，結果挪威的國碼「NO」被解讀成布林值的假，版本號一點一零被解讀成數字一點一，兩個都是靜默的資料損毀。
> 改用序列化器輸出時，字串會被正確加上引號，轉回來也和原資料一致。結論是：讓程式寫格式，不要讓模型手寫格式，並且永遠做來回比對。

=== bullets
heading: Schema 與前端的審查清單
- 約束：主鍵、外鍵、NOT NULL、CHECK、唯一性
- 型別：金額用整數或定點小數；時間存 UTC
- 索引對照實際查詢，用 EXPLAIN 看執行計畫；遷移要能還原
- 前端：AI 輸出是鷹架；檢查響應式、鍵盤操作、對比與無障礙
> 結構定義的審查清單：約束要完整，包括主鍵、外鍵、不得為空、檢查條件與唯一性；金額用整數或定點小數，不用浮點數，時間存世界協調時間；索引要對照實際的查詢，用執行計畫確認；遷移要能還原。
> 前端方面，設計稿轉程式碼的輸出，通常外觀接近、結構與互動不完整，要把它當成鷹架。要檢查的是響應式的斷點、鍵盤操作與焦點順序、色彩對比與無障礙屬性。這類工具常見「可以自動化大部分工作」的宣稱，多半來自工具作者本身，不是量測結果。

=== table
heading: Lab 3：AI 寫的 API 客戶端，用假伺服器測失敗路徑
| 情境 | 結果 |
| 正常 | 成功取得資料 |
| 伺服器錯誤兩次後成功 | 指數退避重試後成功 |
| 404 | 直接失敗，不重試 |
| 非 JSON、缺欄位 | 契約錯誤，直接失敗 |
| 逾時 | 兩次嘗試後失敗，可估算最壞等待時間 |
> 第三個實驗，是一個用標準函式庫寫的介面客戶端，在本機假伺服器上測出每一種結果。正常的請求成功；伺服器錯誤兩次後成功，靠的是指數退避的重試；找不到資源的錯誤直接失敗，不重試；回應不是預期的格式、或缺少欄位，屬於契約錯誤，也直接失敗；逾時則在兩次嘗試後失敗，呼叫端可以算出最壞要等多久。
> 金鑰不要寫在原始碼裡，改從環境變數或祕密管理服務讀取；如果供應商提供介面規格，把規格放進提示詞，可以大幅降低編造端點與參數的機會。

=== quiz
heading: 檢查點
q: 你要為整合測試準備 5 萬筆有外鍵關係的假資料。哪種做法最可靠？
- 請 AI 直接輸出 5 萬筆資料
- 請 AI 輸出 500 筆，再手動複製到 5 萬筆
- * 請 AI 寫一支固定 seed 的產生腳本，由資料庫強制約束，並加上驗證
- 直接複製正式環境的資料
> 檢查點：要準備五萬筆有外鍵關係的假資料，哪種做法最可靠？答案是第三個。產生器可以重現、可以調整規模、可以被審查；直接輸出大量資料昂貴又不可靠，而複製正式資料牽涉隱私與合規。

=== end
heading: 重點回顧
- 要產生器，不要產物
- 讓序列化器寫格式，並做 round trip 比對
- API 客戶端要測失敗路徑，金鑰不寫進原始碼
> 回顧一下。要產生器，不要產物；讓序列化器寫格式，並做來回比對；介面客戶端要測失敗路徑，金鑰不寫進原始碼。
> 思考練習會請你回應一位同事：他用 AI 把二十份設定檔轉了格式，說看起來都對，你要求他補哪些驗證？
