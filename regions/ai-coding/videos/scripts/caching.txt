=== title
heading: Prompt Caching 與成本模型
sub: 快取命中取決於「前綴」完全相同；順序決定一切
> 這一章談提示詞快取。既然每一輪都要重送整段歷史，服務端可以把已經處理過的前綴，它的內部狀態保存起來；下次遇到完全相同的前綴，就直接重用，只處理新增的尾巴。結果是輸入成本便宜很多，延遲也更低。
> 這裡保存的內部狀態，就是鍵值快取。

=== bullets
heading: 像前綴樹一樣比對
- 從第一個 token 開始逐一比對
- 第一個不同的位置之後，全部都無法重用
- 所以：內容的「順序」決定快取能不能命中
> 你可以把它想成前綴樹查表：從第一個 token 開始逐一比對，遇到第一個不同的位置，後面的內容全部都不能重用。所以順序決定一切。
> 就算只差一個 token，那個位置之後也全部要重新處理。所以穩定的部分，必須維持位元組級的完全相同。

=== steps
heading: 排列原則：由穩定到易變
- 工具定義
- system prompt
- 長期文件
- 歷史對話
- 本輪的新訊息
note: 時間戳、隨機 ID 這類每輪都變的東西，放在前面會讓快取每輪失效
> 排列的原則是由穩定到易變：工具定義、系統提示詞、長期文件、歷史對話，最後才是本輪的新訊息。
> 反過來說，任何每一輪都會變的東西，例如時間戳、隨機編號、使用者名稱，只要放在前面，快取每一輪都會失效。在對話中途修改歷史、改工具清單、改系統提示詞，也會讓後面的內容全部失效。
> 實務上，工具清單的排序要固定，不要在中途重新排列；動態的資訊，用附加訊息的方式放在最後。

=== table
heading: 成本結構（相對於一般輸入）
| 類型 | 相對成本 | 意義 |
| 一般輸入 | 1 倍 | 沒有快取 |
| 寫入快取 | 約 1.25 倍 | 第一次處理並保存 |
| 讀取命中 | 約 0.1 倍 | 前綴完全相同時重用 |
note: 以公開的定價機制為例；實際數字請以官方定價頁為準
> 成本結構是這樣的：以公開的定價機制為例，寫入快取比一般輸入略貴，大約一點二五倍；命中讀取則非常便宜，大約只有零點一倍。實際數字請以官方定價頁為準。
> 這代表一件事：只寫不讀的快取，是虧錢的。寫入時多付的溢價，要靠後續的命中才賺得回來。

=== table
heading: 動手：模擬 8 輪代理程式對話
| 設定 | 8 輪總成本（相對） | 相對於不快取 |
| 不快取 | 60,400 | 100% |
| 快取，時間戳在最新訊息尾端 | 約 18,345 | 約 30% |
| 快取，時間戳在 system prompt 開頭 | 75,500 | 125% |
note: 工具加 system 共 3,500 token，每輪新增 900 token；忽略快取過期與輸出 token
> 頁面上的模擬器做的是這件事：工具加系統提示詞共三千五百個 token，每一輪新增九百個 token 的歷史，跑八輪。
> 打開快取時，每一輪新增的部分會被寫入快取；從第二輪開始，前面的前綴都能命中。到了第八輪，一次請求有一萬零七百個 token，只有最後九百個要寫入。
> 不快取的總成本是六萬零四百。打開快取，並把時間戳放在最新訊息的尾端，總成本降到大約一萬八千，只有不快取的百分之三十。
> 但如果把時間戳放在系統提示詞的開頭，每一輪的前綴都不一樣，從來不會命中，卻每一輪都付寫入的溢價，總成本變成不快取的百分之一百二十五，反而更貴。
> 這個模擬忽略了快取過期與輸出 token，只展示前綴結構的影響。

=== bullets
heading: 還要注意的事
- 快取有存活時間；間隔太久會過期，得重新付寫入成本
- 人類慢速互動的代理程式，過期是真實的成本因子
- 上線後監控：快取命中率、每任務成本、首個 token 延遲
> 還有兩件事要注意。快取有存活時間，兩次請求間隔太久，快取就過期，要重新付寫入成本；對人類慢慢互動的代理程式來說，這是真實的成本因子。
> 上線之後，要監控快取命中率、每個任務的成本，以及首個 token 的延遲。命中率突然下降，常常就是有人改了提示詞的強烈訊號。
> 命中率可以這樣算：讀取快取的 token 數，除以總輸入 token 數。
> 另外，快取能保存多久、多短的內容不值得快取，各家的規則都不一樣，設計之前先讀官方文件。用一句話總結這一章：讓前綴保持穩定，讓變化只發生在最後面。

=== quiz
heading: 檢查點
q: system prompt 開頭加了一行「Current time: …」。上線後帳單暴增，最可能的原因？
- 時間戳讓 prompt 變長，所以每輪貴了一點
- * 時間戳每輪都不同又在最前端，整段前綴無法命中，每輪付寫入溢價
- 模型看到日期會自動多生成輸出
- 快取只支援 ASCII 字元
> 檢查點：在系統提示詞開頭加一行目前時間，上線後帳單暴增，最可能的原因是什麼？
> 答案是第二個。時間戳每一輪都不同，又放在前綴的最前面，整段前綴都無法命中快取，每一輪都付寫入的溢價，卻拿不到讀取的折扣。解法是把易變的資訊放到最後，讓穩定的部分維持完全相同。
> 例如把時間附在最新的使用者訊息裡。

=== end
heading: 重點回顧
- 快取靠前綴完全相同；第一個不同之後全部失效
- 由穩定到易變排列內容
- 只寫不讀的快取是虧的
- 把提示詞變更當成需要審查與評測的程式碼變更
> 回顧一下。快取靠的是前綴完全相同；內容要由穩定到易變排列；只寫不讀的快取是虧的。
> 最後一個觀念：提示詞的變更，同時影響品質與成本，應該當成需要審查與評測的程式碼變更來處理。思考練習會請你說明，上線後要監控哪些指標。
