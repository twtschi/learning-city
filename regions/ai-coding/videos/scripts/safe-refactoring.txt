=== title
heading: 安全重構
sub: 沒有判定依據，就沒有「行為不變」
> 重構常被認為是 AI 工具的強項。但重構的定義裡就包含「行為不變」，所以每一次重構都需要判定依據來證明，AI 做的重構尤其如此。這一章用三個實驗說明這件事。

=== bullets
heading: 常見的重構手法
- 解開難讀的炫技程式碼
- Extract method：把專注於某件事的片段抽成新函式
- Decompose conditional：把冗長的條件式抽成命名清楚的方法
- 改名，以及刪除不再使用的程式碼
> 常見的重構手法有幾種：解開難讀的炫技程式碼；把長函式裡專注於某件事的片段抽成新函式；把冗長的條件式抽成命名清楚的方法，例如把「使用者已啟用、有訂閱、沒有被封鎖」抽成「可以存取內容」；以及改名和刪除不再使用的程式碼。

=== steps
heading: 重構的判定依據，由便宜到昂貴
- 編譯器與型別檢查
- 既有的測試
- 特徵化測試：先把現在的行為記錄下來
- 差分測試：同一批輸入跑新舊兩版，逐筆比較
> 重構的判定依據有四種，由便宜到昂貴。第一，編譯器與型別檢查，抓得住改名遺漏與簽章不一致。第二，既有的測試，但它只保護有測試的行為。第三，特徵化測試：沒有測試的舊程式，先把現在的行為記錄下來，不管對錯，再動手改。第四，差分測試：對同一批輸入跑新舊兩版，逐筆比較，這是 AI 改寫最主要的驗證手段。

=== table
heading: Lab 1：炫技程式碼與重構版，真的等價嗎？
| 輸入 n | 原版 | 重構版 | 結果 |
| 1 到 30 的正整數 | 相同 | 相同 | 一致 |
| 0 | 無窮迴圈 | 0 | 不同 |
| -3 | 無窮迴圈 | 0 | 不同 |
| 2.5 | 無窮迴圈 | 1 | 不同 |
note: 對舊版一定要加逾時，因為舊版可能不會結束
> 第一個實驗，是一行炫技的費氏數列程式，和常見的迴圈重構版做差分測試。在一到三十的正整數範圍內，兩者完全一致。但當輸入是零、負數或小數時，原版的迴圈永遠不會結束，重構版則回傳一個數值。
> 這次的行為改變剛好是好的方向，把無窮迴圈變成有限的結果，但它仍然是行為改變。AI 說「這是等價的重構」，是一個主張，不是證據。你要自己定義等價的範圍，並用差分測試證明；而且對舊版一定要加逾時。

=== code
heading: Lab 2：條件式「整理得更漂亮」，副作用跟著變了
```python
def can_access_v1(u):
    return is_active(u) and has_subscription(u) and not_blocked(u)

def can_access_v2(u):      # 看起來更整齊
    return all([is_active(u), has_subscription(u), not_blocked(u)])

# 回傳值相同
# v1 呼叫: ['is_active']
# v2 呼叫: ['is_active', 'has_subscription', 'not_blocked']
```
> 第二個實驗。AI 常見的一種簡化，是把串接的「而且」條件，換成先建立一個串列再全部檢查。回傳值完全相同，所以只看輸出的測試會全部通過。
> 但新寫法會先把三個函式都呼叫完才判斷，短路求值消失了。原本使用者沒有啟用時就會停下來，現在每次都多查兩次資料庫。抽出方法或拆解條件時要檢查三件事：求值順序、短路行為，以及例外傳播。測試要能看到呼叫的次數與順序，光比對回傳值不夠。

=== bullets
heading: Lab 3：為什麼「讓 AI 找 dead code」風險高
- 只看名稱引用：四個函式看起來都沒被用到
- 實際上兩個是用字串動態呼叫，一個是對外的進入點
- 需要進入點、動態分派、反射、序列化名稱等資訊
- 用專門工具，設定進入點與白名單；刪除用獨立的提交
> 第三個實驗示範為什麼讓 AI 找不再使用的程式碼風險很高。一個只看名稱引用的簡單分析，判定四個函式都沒被用到；實際上，只有一個真的沒用，兩個是用字串動態呼叫的處理函式，還有一個是對外的進入點。
> 真正的偵測需要進入點、動態分派、反射、序列化名稱這些資訊，這正是看一段程式碼做不到的部分。實務上要用專門的工具，設定進入點與白名單；先加上執行期的觀測再決定刪除；刪除要用獨立的提交，方便還原。

=== bullets
heading: 改名與標準流程
- 改名用語意工具，不用文字取代；再檢查字串、設定、文件、對外 API
- 一次只做一種重構，提交要小
- 改動前後跑同一套測試，再加上差分測試
- 重構與功能變更不要放在同一個合併請求
> 改名也一樣，要用開發環境或語言伺服器的語意改名，而不是文字取代；再用全域搜尋檢查字串、設定檔、文件與對外介面。AI 適合提出更好的名稱，而不是執行跨檔案的改名。
> 把重構交給 AI 的標準流程是：先確認判定依據；一次只做一種重構，提交要小；改動前後跑同一套測試，再加上差分測試；而且重構與功能變更，不要放在同一個合併請求裡。

=== quiz
heading: 檢查點
q: AI 把 `a() and b() and c()` 改成 `all([a(), b(), c()])`，測試全部通過。為什麼仍可能是迴歸？
- all 比 and 慢，所以一定是迴歸
- * 串列會先把三個函式都呼叫一次，短路求值消失；只比對回傳值的測試看不出來
- all 只能用在數字上
- 這是合法的風格改動，不影響行為
> 檢查點：條件式被改成先建立串列再全部檢查，測試全部通過，為什麼仍可能是迴歸？答案是第二個。重構要保留的是可觀察的行為，包含副作用與呼叫次數。

=== end
heading: 重點回顧
- 重構需要判定依據；「等價」是要被證明的主張
- 求值順序、短路、例外傳播都屬於行為
- dead code 與改名要用專門工具
> 回顧一下。重構需要判定依據，等價是要被證明的主張；求值順序、短路與例外傳播都屬於行為；找不再使用的程式碼與改名，要用專門的工具。
> 思考練習會請你設計一個流程，讓團隊可以放心把一個五千行、幾乎沒有測試的舊模組交給 AI 重構，並說明什麼時候應該停手。
