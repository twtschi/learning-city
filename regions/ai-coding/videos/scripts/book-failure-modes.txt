=== title
heading: AI 輔助開發中真實出現的失敗
sub: 最有價值的不是成功的部分，而是每一次必須人工介入的地方
> 這一章以一個用 AI 工具從頭做出應用的實作過程為例。最有價值的，不是成功的部分，而是每一次必須由人介入的地方。這些介入，可以直接當成失敗模式的案例庫。

=== figure
heading: 生成、執行、觀察、修正
src: intervention-loop.svg
caption: 每次人工介入，都是一筆可以記錄的資料
> 這張圖是一個迴圈：生成、執行、觀察、修正。每一次人工介入，都是一筆可以記錄的資料，之後可以變成規則檔的一行、一個自動檢查，或評測裡的一個案例。
> 實務上，每接受一個建議，就驗證一次功能，也留意相關功能有沒有出現副作用。當 AI 不理解全貌時，就要準備好手動接管。

=== steps
heading: 五個真實的失敗
- 只走成功路徑：理想情況能跑，但缺少錯誤處理
- 對你的程式做了不存在的假設：測試呼叫了不存在的方法
- 看起來對，但沒解決真正的問題：產生只能用一次的新 ID
- 狀態與生命週期錯誤：每個方法各自建立連線與游標
- 邊界條件：複製資料庫時沒有排除內部的系統資料表
> 案例有五類。第一，只走成功路徑：理想情況可以跑，但缺少錯誤處理與強化，重構時應該優先補強。第二，對你的程式做了不存在的假設：為某個類別產生的測試，假設了錯誤的建構方式，呼叫了專案裡不存在的方法，測試根本跑不起來。
> 第三，看起來對，但沒解決真正的問題：資料庫的遞增編號出現衝突，助手照字面產生了一個只能用一次的新編號，之後又建議了該資料庫不支援的寫法，最後是靠人對資料庫自動遞增行為的了解才解決。
> 第四，狀態與生命週期錯誤：重構後每個方法各自建立連線與游標，執行時出錯，改成共用才解決。第五，邊界條件：把資料庫複製到記憶體時，沒有排除內部的系統資料表，導致錯誤，要再調整查詢。

=== code
heading: 讓資料庫自己產生 ID
```sql
CREATE TABLE question_sets (
    question_set_id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id      INTEGER NOT NULL,
    question_id     INTEGER NOT NULL
);
-- 給 NULL，SQLite 會自動配發下一個 ID；每一筆都成立，不只第一筆
INSERT INTO question_sets (question_set_id, session_id, question_id)
VALUES (NULL, 6, 17);
```
> 以編號衝突為例，比較穩的做法是讓資料庫自己產生編號：把主鍵設成自動遞增，插入時給空值，資料庫就會配發下一個編號。這樣每一筆都成立，而不只是第一筆。
> 審查 AI 產生的 SQL 時，也要檢查幾件事。避免用星號選取所有欄位、檢查 WHERE 條件、留意索引、考慮交易，並確認錯誤處理。改完之後，也要實際查看資料庫裡的狀態。

=== table
heading: 把案例變成分類法，每一類配一個防線
| 失敗模式 | 防線 |
| 幻覺的 API 或簽名 | 讀真實定義、型別檢查、語言伺服器 |
| 對平台特性的錯誤假設 | 在目標環境實際執行並觀察 |
| 狀態與生命週期 | 整合測試；資源管理慣例寫進規則檔 |
| 邊界條件 | 要求列出邊界案例並寫成測試 |
| 只走成功路徑 | 審查清單、故障注入測試 |
| 需求誤解 | 驗收測試先於實作 |
> 把這些案例抽象成分類法，每一類配一個可以自動化的防線，就是評測與 harness 設計的起點。幻覺的介面，用讀真實定義和型別檢查來防；對平台特性的錯誤假設，在目標環境實際執行；狀態與生命週期，用整合測試，並把資源管理慣例寫進規則檔；邊界條件，要求列出邊界案例並寫成測試；只走成功路徑，用審查清單與故障注入；需求誤解，則讓驗收測試先於實作。
> 對照剛才的案例：不支援的 SQL 寫法，是對平台特性的錯誤假設；連線與游標重複建立，屬於狀態與生命週期；系統資料表或空輸入，屬於邊界條件；照字面做卻沒解決問題，則是需求誤解。

=== quiz
heading: 檢查點
q: 助手為你的類別產生的單元測試，呼叫了專案中不存在的方法。這屬於哪類失敗，哪個防線最直接？
- 取樣的隨機性；把 temperature 設成 0
- * 幻覺的 API 或錯誤假設；先讀真實定義並實際執行測試，用型別檢查提早發現
- 訓練資料過時；等下一版模型
- context window 太小；換更大的 window
> 檢查點：產生的測試呼叫了不存在的方法，屬於哪一類？答案是第二個，幻覺的介面或錯誤假設。降低溫度不能讓它看到真實的定義；最直接的做法，是讓它讀到真實的簽名，並用執行結果當作回饋。
> 先在原始碼裡搜尋這個方法和類別的真實定義，再實際跑一次測試；測試失敗或型別錯誤，就是最直接的回饋。

=== end
heading: 重點回顧
- 每一次人工介入都是資料
- 失敗模式要配上可自動化的防線
- 從真實紀錄出發，用頻率與嚴重度排序
> 回顧一下。每一次人工介入都是資料；每一類失敗模式，都要配上一個可以自動化的防線；分類要從真實的紀錄出發，再用頻率與嚴重度排序，優先處理最常見、代價最高的類別。
> 一個可以從今天開始的做法：每次人工介入，就記一行，寫下發生了什麼、為什麼要介入、下次怎麼自動擋下。一個月之後，這份紀錄就是你們團隊最有價值的評測資料。
> 思考練習會請你為寫程式的代理程式設計一套失敗模式分類，並說明每一類怎麼偵測與防止。提示是：先蒐集真實的失敗案例，人工標註成因，而不是憑空列出類別；每一類再配一個自動化的偵測，例如型別檢查、測試、執行觀察，或檢查修改的範圍。
