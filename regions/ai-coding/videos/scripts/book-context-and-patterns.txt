=== title
heading: Context 從哪來
sub: 助手看起來「懂你要做什麼」，不是魔法，而是有東西被放進了 context
> 歡迎來到第二週。這一週談 AI 協作開發的工作流程，這一章先回答一個基本問題：程式助手是怎麼知道你在做什麼的？答案很樸素：不是魔法，而是有東西被放進了上下文。放進去的東西不對，建議就會不對。

=== bullets
heading: IDE 型助手蒐集的 context
- 目前編輯的檔案、相鄰分頁的內容
- 工作區或解決方案的結構
- 游標前後的程式碼（fill-in-the-middle：也看後面已經有什麼）
- 專案層級：repo 資訊、PR 與 issue、文件與設定檔
> 開發環境裡的助手，通常會蒐集這些資料：目前編輯的檔案、相鄰分頁的內容、整個工作區的結構，以及游標前後的程式碼。這裡有一個技巧叫填中間，英文是 fill-in-the-middle，簡稱 FIM。它不只看你寫到哪裡，也看後面已經寫了什麼。
> 專案層級的理解，則來自程式庫的資訊、合併請求與問題單、文件與設定檔。企業版的方案，通常比個人版看得更深。
> 這也解釋了一個常見的現象：同一段提示詞，在兩個不同的工具裡得到不同的結果。原因往往不在模型，而在兩個工具放進上下文的東西不一樣。

=== steps
heading: 七個可以反覆使用的提問模式
- 找出選取程式碼中的錯誤
- 重構以提升品質（安全、速度或資源）
- 為特定任務產生樣板程式碼
- 解釋這段程式碼怎麼運作
- 補測試；提出可讀性與可維護性的改進
- 比較兩個方案的取捨
> 接著是一組可以反覆使用的提問模式：找出選取程式碼中的錯誤；以安全、速度或資源為目標重構；為連資料庫、讀檔、送網頁請求這類任務產生樣板；解釋一段程式碼怎麼運作；補上測試；提出可讀性與可維護性的改進；以及比較兩個方案的取捨。它們的共同點，是把意圖講得非常明確。其中解釋程式碼這一招，在讀舊程式或別人的程式時特別有用。

=== bullets
heading: 為什麼不把整個專案都放進 context
- 雜訊會稀釋模型的注意力
- 回應變慢，也比較不準
- 精準挑選相關檔案，比全部塞進去有效
> 一個常見的疑問是：為什麼要自己挑選檔案，而不是把整個專案都放進去？答案是雜訊會稀釋模型的注意力，讓回應變慢，也比較不準。精準挑選相關的檔案，通常比全部塞進去有效。

=== code
heading: 規則檔：把團隊慣例變成每次都會載入的 context
```markdown
# AGENTS.md
## 建置與測試
- 建置單一模組：bazel build //net/rpc:all
- 只跑相關測試：bazel test //net/rpc:client_test
## 約定
- C++17；用 absl::Status 回報錯誤，不要丟例外。
- 新的公開 API 必須附 *_test.cc。
## 禁區
- 不要修改 third_party/ 與 generated/。
```
> 各家工具都支援專案層級的規則檔，本質相同：一份每次都會被載入的專案說明。該放的是建置與測試指令、架構約定、不能動的目錄、風格與命名慣例、常見陷阱。這樣團隊就能把編碼標準直接寫進 AI 的行為裡。
> 畫面上是一份給 C++ 大型單一程式庫用的示意：寫明建置單一模組、只跑相關測試的指令；用狀態物件回報錯誤，不要丟例外；新的公開 API 必須附測試；不要修改第三方與自動產生的目錄。
> 不該放的是很快過期的細節、整份介面文件、長篇的背景故事，因為它每一輪都在付費，越短越好。規則檔也要像程式碼一樣維護：放進版本控制、有負責人、改動要審查。規則檔過期造成的錯誤很難除錯，因為看起來就像模型變笨了。

=== quiz
heading: 檢查點
q: 助手產生的程式碼呼叫了專案裡根本不存在的 helper 函式。最可能的 context 問題與處理？
- 模型壞了，換更大的模型
- temperature 太高，改成 0
- * 定義該函式的檔案沒進入 context；只加入相關檔案，並在規則檔寫明共用函式的位置
- 把整個 repo 都貼進去
> 檢查點：助手呼叫了專案裡根本不存在的輔助函式，最可能是什麼問題？答案是第三個。它多半是看不到真正的定義，或是定義雖然進了上下文，卻被雜訊稀釋了。精準加入相關檔案，再用規則檔指出共用函式的位置，比全部塞進去有效；全塞進去，反而可能稀釋重點。

=== end
heading: 重點回顧
- 助手的「理解」來自被放進 context 的東西
- 把意圖講明確：用固定的提問模式
- 精準挑選，而不是全部塞進去
- 規則檔要短、要維護、要審查
> 回顧一下。助手的理解，來自被放進上下文的東西；把意圖講明確；精準挑選檔案，而不是全部塞進去；規則檔要短、要維護、要審查。
> 思考練習會問你：在一個五百萬行的大型程式庫裡，怎麼讓代理程式找到正確的程式碼，又遵守團隊慣例？提示是分層的規則檔、按需搜尋的工具，以及可以執行的建置與測試指令。
> 例如根目錄放通用的建置與風格規範，子目錄放各模組自己的約定，讓代理程式只載入相關的部分。搜尋工具可以是 ripgrep、符號索引或 LSP，讓代理程式按需讀檔，並限制單次的讀取量；再用評測，在同一組任務上比較不同的上下文策略，量化成功率與成本。
