=== title
heading: Tool Use：誰真正執行了工具
sub: 模型只提出請求，執行與驗證都在你的程式
> 這一章談工具使用，也是第一週最後一個互動章節。很多人以為模型會自己去讀檔、執行指令。事實上，模型只會提出請求，真正的執行與驗證，都在你的程式裡。

=== steps
heading: 一次完整的往返
- 請求中宣告工具：名稱、描述、參數的 JSON Schema
- 模型回應一個結構化區塊：「我想呼叫工具 X，參數是 Y」
- harness 決定要不要執行、怎麼執行
- 結果以 tool_result 送回模型，模型繼續下一步
> 一次完整的往返是這樣的。第一，你在請求裡宣告工具，包括名稱、描述，以及參數的結構定義。第二，模型在回應裡用一個結構化的區塊表示：我想呼叫某個工具，參數是什麼。
> 第三，由你的程式，也就是 harness，決定要不要執行、怎麼執行。第四，把結果送回模型，模型再決定下一步，直到它表示完成為止。頁面上的實驗可以一步一步播放這個往返。

=== big
heading: 用 RPC 來理解
text: 模型像沒有權限的遠端呼叫者；harness 是伺服器加上政策引擎
> 用熟悉的概念來理解：模型像一個沒有權限的遠端呼叫者，harness 則是遠端呼叫的伺服器，再加上一個政策引擎。你不會信任客戶端傳來的參數，同樣也不該信任模型產生的參數。

=== compare
heading: 責任分工
col: 模型
- 依工具描述與當下的 context，決定是否呼叫
- 產生參數
- 不執行任何東西
col: Harness
- 解析呼叫、驗證參數（結構、路徑範圍、危險指令）
- 取得授權、真正執行、設定限額
- 把結果或錯誤送回模型
> 責任分工很清楚。模型負責依照工具描述和當下的 context，決定要不要呼叫，以及產生參數，它不執行任何東西。
> harness 負責解析呼叫、驗證參數，例如結構是否正確、路徑是否在允許的範圍、指令是否危險；然後取得授權、真正執行、設定限額，最後把結果或錯誤送回去。

=== bullets
heading: 三個實務重點
- 就算有結構化輸出的約束，harness 端也要再驗證
- 驗證失敗時，回傳具體、可行動的錯誤訊息，並設重試上限
- 工具描述就是模型看到的 API 文件；回傳的內容是資料，不是指令
> 三個實務重點。第一，就算啟用了結構化輸出的約束，harness 端也一定要再驗證一次。
> 第二，驗證失敗時，把清楚的錯誤訊息送回去，說明哪個欄位錯了、期望的是什麼，模型通常能自己修正重試；同時設定重試上限，避免死循環。
> 第三，工具的描述，就是模型看到的 API 文件，名稱含糊、描述不清，都會降低成功率。而工具回傳的內容，例如檔案、網頁、問題單，可能夾帶惡意指令；它是資料，不是指令。這在第六週會專門處理。

=== quiz
heading: 檢查點
q: 模型回傳的工具參數是讀取 `../../etc/passwd`。誰該負責擋下它？
- 模型，因為 system prompt 已經叮嚀過
- * harness 與沙箱：路徑白名單、唯讀掛載、權限確認
- 使用者，每次都要人工檢查
- 不需要擋，模型不會真的這樣做
> 檢查點：模型回傳的參數，是要讀取系統裡存放帳號資訊的檔案路徑，誰該負責擋下它？
> 答案是 harness 與沙箱。提示詞裡的叮嚀只是請求，不是安全邊界。真正的邊界在系統設計：路徑白名單、唯讀掛載、網路隔離、權限確認。

=== end
heading: 重點回顧
- 模型只提出工具呼叫；執行、驗證、授權都在 harness
- 不信任模型產生的參數，就像不信任客戶端
- 錯誤訊息要能教模型怎麼修，並設重試上限
- 工具回傳的內容是資料，不是指令
> 回顧一下。模型只提出工具呼叫，執行、驗證、授權都在 harness；不要信任模型產生的參數；錯誤訊息要能教模型怎麼修；工具回傳的內容是資料，不是指令。
> 一個簡單的自我檢查：拿你常用的一個工具定義，問自己三件事。名稱與描述有沒有說清楚什麼時候該用它？參數是不是夠窄，能用列舉就不要用自由字串？出錯時的訊息，能不能教模型怎麼修？
> 思考練習會請你描述一次完整的工具呼叫往返，並說明參數不合規格時系統該怎麼做。第一週的互動章節到這裡結束，接下來的筆記章節會把這些觀念接到實際的開發工作上。
