=== title
heading: Token 與 Context Window
sub: 模型看到的不是字，而是一串整數；上下文視窗是預算，不是記憶
> 歡迎來到 AI Coding。這一章要建立兩個每天都會用到的直覺：第一，模型看到的不是文字，而是 token；第二，context window 是一次請求的預算，不是模型的記憶。
> 這兩件事決定了成本、延遲，也決定了代理程式為什麼會「忘記」或「記得」東西。

=== bullets
heading: 模型的輸入與輸出單位是 token
- tokenizer 把文字切成子字串，每段對應一個整數 ID
- 模型只吃整數序列，輸出下一個 token 的機率分佈
- 計費、延遲、上下文上限，全部用 token 計算
note: 把 tokenizer 想成編譯器的 lexer：文字進去，整數序列出來
> 先看第一個觀念。大型語言模型的輸入和輸出單位是 token，也就是由 tokenizer 切出來的子字串，每一段對應到詞表裡的一個整數。
> 如果你寫過編譯器，可以把 tokenizer 想成 lexer：文字進去，整數序列出來。模型本身只處理整數序列，它每一步輸出的，是下一個 token 的機率分佈。
> 因為計費、延遲和上下文上限都用 token 計算，「這段提示詞大概多少 token」是你每天都要有感覺的數字。

=== table
heading: 粗估 token 數的經驗法則
| 內容 | 大約的密度 | 備註 |
| 中日韓文字 | 每個字約 1 個 token | 常比英文散文密 |
| 英文單字 | 約每 4 個字母 1 個 token | 常見字可能整個是 1 個 |
| 數字與標點 | 常各自成為 token | 程式碼的符號很吃預算 |
note: 這只是粗估；不同模型的 tokenizer 不同，正式計算請用 API 的 token 計數功能
> 在課程的互動實驗裡，有一個粗估工具。它用很簡單的規則：中日韓文字大約一個字一個 token，英文大約每四個字母一個 token，數字與標點常常各自成為一個 token。
> 這只是粗估，真實的 tokenizer 會因模型而不同，正式計算要用 API 提供的 token 計數功能。
> 但這個粗估已經能說明一件事：中文與程式碼的 token 密度，通常比英文散文高。程式碼裡的縮排、括號、運算子都會吃 token，所以讀一個大檔案，很快就會用掉大量預算。

=== big
heading: 第二個觀念
text: Context window 是一次請求的預算，不是模型的記憶
> 第二個觀念是這一章的重點。context window 是一次請求裡，輸入加輸出能容納的 token 上限。它不是模型的長期記憶。

=== steps
heading: 每一輪對話，其實都是重送整段歷史
- 模型本身沒有狀態，推論時權重不會改變
- 你的程式，也就是 harness，每一輪把歷史訊息重新組進 context
- 模型在「這一輪」的 context 裡讀到先前的內容，所以看起來像記得
> 模型本身沒有狀態，推論的時候權重不會改變。那為什麼代理程式在第四十輪，還答得出第一輪的需求？
> 答案是：你的程式，也就是 harness，每一輪都把整段歷史重新組進 context，再送一次。模型是在這一輪的 context 裡讀到了第一輪的內容。
> 所以，代理程式的「記憶」，其實是 harness 每一輪重組 context 的結果。這也是為什麼截斷、摘要、檢索這些 context 管理的技術，會是代理程式工程的核心。

=== compare
heading: 容納得下，不等於用得好
col: 容納得下
- 規格上可以放進很長的內容
- 每一輪都要重送、重新處理，成本與延遲跟著增加
col: 用得好
- 放得越滿，越容易漏掉中間的細節
- 長上下文的檢索品質會隨長度與位置變化，要用自己的任務量測
> 要把兩件事分開：容納得下，和用得好。
> 規格表告訴你可以放進很長的內容，但每一輪都要重送、重新處理，成本與延遲都會增加。
> 更重要的是品質：放得越滿，模型越可能漏掉中間的細節，或被無關的內容干擾。長上下文下的檢索品質，會隨長度與位置變化，這必須用你自己的任務去量，不能只看規格表。

=== quiz
heading: 檢查點
q: 代理程式對話到第 40 輪，使用者問「還記得我第一輪的需求嗎？」模型答對了。最準確的解釋是？
- 模型把對話存進長期記憶，每輪更新
- * harness 每輪都把含第一輪的歷史重新送進 context，模型在當輪讀到它
- API 伺服器依 session 保存狀態，模型直接查詢
- 模型權重在對話中被微調，學會了這個需求
> 來看這一章的檢查點。代理程式對話到第四十輪，使用者問它還記不記得第一輪的需求，它答對了。最準確的解釋是哪一個？
> 答案是第二個：harness 每一輪都把包含第一輪的歷史重新送進 context。其他選項都假設模型有某種狀態，但模型本身是無狀態的，權重在推論時不會改變。

=== end
heading: 重點回顧
- 模型處理的是 token；成本、延遲、上限都用 token 算
- 中文與程式碼的 token 密度通常比英文高
- Context window 是預算：harness 每輪重組 context
- 長 context 要量測品質，不要假設「放得下就用得好」
