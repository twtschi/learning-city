heading: AI 開發工具地圖與導入考量
sub: 產品名會過期，評估的維度不會
> 這一章整理 AI 開發工具的版圖，以及導入時要考慮的事。工具更新得非常快，所以這一章的重點不是記住產品名稱，而是學會用不會過期的維度去比較工具。

=== compare
heading: 兩大類工具
col: 整合在 IDE 裡
- 直接看到你的程式碼當 context
- 適合寫程式的當下使用
col: 獨立的聊天介面
- 通用對話
- 實務上比較適合設計、討論這類抽象工作
note: 這個分類已經模糊：許多 IDE 工具有聊天視窗，聊天產品也有代理模式
> 常見的分法是兩大類。一類整合在開發環境裡，直接看得到你的程式碼，適合在寫程式的當下使用。另一類是獨立的聊天介面，通用對話，實務經驗上比較適合設計與討論這類抽象層面的工作。
> 不過這個分類已經越來越模糊，許多開發環境裡的工具都有聊天視窗，聊天產品也有代理模式。要記的不是產品名，而是差異從哪裡來：上下文怎麼取得、能不能直接改檔案、能不能執行指令。

=== bullets
heading: 補全與生成的差別
- 傳統補全：依賴語言規則與已知的符號
- 生成式工具：依靠從大量程式碼學到的模式
- 可以根據註解或需求，產生整段實作，範圍涵蓋整個檔案與專案
> 補全與生成也不一樣。傳統的程式碼補全，依賴語言規則與已知的符號；生成式的工具，則依靠從大量程式碼學到的模式，可以根據註解或需求，產生整段實作，範圍可以涵蓋整個檔案甚至整個專案。

=== figure
heading: 一次請求經過什麼
src: copilot-pipeline.svg
caption: 你看到的建議，是 context 蒐集、前處理、模型與後處理的總和
> 這張圖是一次請求在開發環境助手裡的簡化管線。去程：編輯器先蒐集上下文，包括游標前後的程式碼、開啟的分頁、檔名與專案結構；送到代理伺服器做過濾；模型產生建議。回程：再過濾一次，檢查品質與安全，並且可以選擇是否比對公開程式碼。
> 其中，游標前後的程式碼都會送出，讓模型填補中間的空缺。代理伺服器則會先擋下惡意操控的企圖，再做毒性與個資的過濾。
> 這張圖的啟示是：工具不等於模型。你看到的建議，是上下文蒐集、前處理、模型與後處理的總和。比較兩個工具時，差別常常不在模型，而在上下文與管線。

=== bullets
heading: 導入時要考慮的事
- 資料品質與授權：產出與既有程式碼過於相似時的法律問題
- 和既有工作流整合：IDE 設定、團隊風格的一致性
- 團隊約定：如何標記 AI 輔助的程式碼、與 code review 的關係
- 專有程式碼送進工具的安全顧慮，以及一致的使用權限
> 導入時要考慮幾件事。第一，資料品質與授權，也就是產出和既有程式碼過於相似時的法律問題，目前仍有爭議。第二，和既有工作流的整合，包括開發環境的設定與團隊風格的一致性。
> 第三，團隊層面的約定：如何標記 AI 輔助的程式碼、它和程式碼審查的關係、專有程式碼送進工具的安全顧慮，以及全員一致的使用權限。AI 產生的程式碼，要符合和人寫的相同標準，使用情況也要透明。

=== table
heading: 用不會過期的維度比較工具
| 維度 | 要問的問題 |
| context 取得方式 | 手動貼上、目前檔案、整個 repo，還是代理程式自行搜尋？ |
| 自主程度 | 補全、聊天，還是代理程式？ |
| 修改機制 | diff 預覽、直接寫檔、能否執行指令？ |
| 資料與合規 | 程式碼是否離開公司、保存政策？ |
| 可客製、成本、可量測性 | 規則檔與 MCP、成本結構、有沒有日誌與指標？ |
> 比較工具時，可以用這些維度：上下文怎麼取得，是手動貼上、只看目前的檔案、整個程式庫，還是代理程式自己去搜尋；自主程度是補全、聊天，還是代理程式；修改機制是預覽差異、直接寫檔，還是能執行指令；資料與合規，程式碼會不會離開公司；最後是可客製、成本結構，以及有沒有日誌與指標可以量測。
> 評估表可以很簡單，重點是每一個分數都附上證據，例如你讓工具實際做過的任務紀錄。
> 例如每個維度給一到五分；上下文取得這一項，就問它能自己搜尋程式庫，還是只能看開啟的檔案。

=== quiz
heading: 檢查點
q: 你要為 200 人的工程組織評估 AI coding 工具。哪個做法最成熟？
- 選市佔率最高的產品，全公司開通
- 讓每位工程師各自決定，不收集任何資料
- * 定義評估維度與任務集，在代表性的 repo 上讓各工具做同一組任務並記錄結果與失敗案例
- 以官網 demo 的表現為準
> 檢查點：為兩百人的工程組織評估工具，哪個做法最成熟？答案是第三個。工具變化很快，展示影片不代表你的程式庫；有可比較的任務集、有資料合規的檢查、有失敗案例的紀錄，才能做出可以被挑戰、也可以被修正的決策。
> 實際做這個決定時，先釐清目標與風險：要提升速度、品質還是上手時間，哪些程式碼不能離開公司。再用同一組代表性任務跑每個候選工具，蒐集完成率、人工介入的次數、審查發現的問題，以及開發者的回饋。

=== end
heading: 重點回顧
- 差異來自 context 取得、修改機制與執行能力，不只是模型
- 工具等於模型加上整條管線
- 導入真正費工的是建立證據：基線、對照試行、失敗案例庫
> 回顧一下。工具之間的差異，來自上下文怎麼取得、修改機制與執行能力，不只是模型；工具是模型加上整條管線。導入真正費工的地方，不是挑一個工具，而是建立證據：定義基線指標、做有對照的試行、累積失敗案例庫，再決定擴大或停止。
> 試行之後，要給出建議與停損條件，並規劃使用慣例，例如標記 AI 輔助、審查要求與權限設定。
