Taulli 在第 1 章把「讀懂不熟悉的程式」與「大型遺留系統現代化」列為 AI 輔助最有價值的場景之一（p.8、p.12–14）。對 staff engineer 來說，這兩件事風險都高：**讀懂**錯了，後續全部決策建立在錯的理解上；**移植**錯了，錯誤會悄悄進入正式環境，而且往往發生在金額與日期這類細節上。這一篇先看書怎麼說，再用實驗看「看起來正確的翻譯」是怎麼出錯的。

標示方式：**【書】** 書中的說法（附頁碼）；**【實測】** 我在沙箱實際執行的結果；**【判斷】** 我的工程判斷。

## 書的內容

**用 AI 讀程式（p.8、p.13–14）**

- **【書】** 作者展示了一個 Fortran 程式片段（模組、複數型別、重載的加法運算子），你完全看不出它是什麼語言。把它貼給 ChatGPT 並問「這是什麼語言？這段在做什麼？怎麼運作？」，它辨認為 Fortran 90/95 以上的版本，並逐段說明模組、型別定義與運算子重載（p.13–14）。
- **【書】** 這類 AI 也能當「顧問」：對不熟的語言或框架提供入門說明、拆解不同程式碼庫，讓開發者更快上手（p.8）。

**大型遺留系統現代化（p.12–13）**

- **【書】** 作者引用 Marc Andreessen 的「軟體正在吞噬世界」，說明大型企業背著昂貴又難以現代化的遺留系統（p.12）。
- **【書】** IBM 在 2023 年 10 月推出 watsonx Code Assistant for Z，可把主機上的 COBOL 轉成 Java，輸出為物件導向；書中說其模型涵蓋 115 種程式語言、以 1.5 兆個 token 訓練、約 200 億參數（p.12）。
- **【書】** 全球仍有數千億行的 COBOL，而且往往已有數十年、文件很少；書舉的例子包括信用卡處理與美國的學生貸款系統（p.12）。加州 DMV 投入 2.08 億美元的現代化專案，數年後喊停（p.12）。
- **【書】** 傳統的程式碼轉譯器（transpiler）存在已久，但它通常只是把 COBOL 的義大利麵條式程式碼，快速翻成 Java 的義大利麵條式程式碼，只是換了外觀（p.13）。書說 IBM 稱生成式 AI 讓專案成果提升多達十倍（p.13）。這是廠商的說法，書中沒有給出獨立驗證。

## 「翻譯」與「現代化」是兩件事【判斷】

| | 忠實移植 | 重新設計 |
|---|---|---|
| 做法 | 逐段翻成新語言，保持結構 | 依新平台的慣用結構重寫 |
| 風險 | 低：行為較容易對照 | 高：行為可能改變，要重新驗證 |
| 收益 | 低：問題原封不動搬家，書中所謂的「換外觀」 | 高：可維護性與效能改善 |
| 需要的 oracle | 舊系統本身 | 舊系統加上新的規格與測試 |

AI 讓兩者的「寫出來」都變便宜，但**驗證成本不變**，甚至更高，因為輸出量變大。結論：**舊系統就是 oracle**，所有策略都應該圍繞它設計。

## 實驗：看起來沒問題的翻譯，在哪裡出錯

假設舊系統（以下是我的假設，用來示範，不是實際的 COBOL 程式）以**整數「分」**計算 1.5% 的手續費，並**四捨五入（遠離零）**到分。一個常見的「直譯」會改成浮點數與內建的 `round`；另一個「更小心」的版本改用 `Decimal`，但沒指定捨入模式。

```python
import random
from decimal import Decimal, ROUND_HALF_UP

def legacy_fee(cents: int) -> int:            # 舊系統（假設）：整數分，1.5%，四捨五入（遠離零）
    return int((Decimal(cents) * Decimal("0.015")).quantize(Decimal("1"), rounding=ROUND_HALF_UP))

def port_float(cents):   return round(cents * 0.015)                                              # 直譯：浮點數加內建 round
def port_decimal(cents): return int((Decimal(cents) * Decimal("0.015")).quantize(Decimal("1")))  # 改用 Decimal，但沒指定捨入模式
def port_int(cents):     return (cents * 15 + 500) // 1000                                        # 純整數運算

typical = [100, 250, 1000, 5000, 9999, 20000, 123456]
print("典型案例全部一致:", all(legacy_fee(c) == port_float(c) == port_decimal(c) == port_int(c) for c in typical))

rng = random.Random(1)
cases = [rng.randint(1, 1_000_000) for _ in range(200_000)]
for name, fn in [("float + round", port_float), ("Decimal（預設捨入）", port_decimal), ("整數運算", port_int)]:
    bad = [c for c in cases if fn(c) != legacy_fee(c)]
    ex = ", ".join(f"{c}分: 舊={legacy_fee(c)} 新={fn(c)}" for c in bad[:2])
    print(f"{name:20s} 不一致 {len(bad):6d} / {len(cases)} ({len(bad)/len(cases):.1%})  {ex}")
```

**【實測】** 輸出：

```text
典型案例全部一致: True
float + round        不一致    503 / 200000 (0.3%)  886700分: 舊=13301 新=13300, 355100分: 舊=5327 新=5326
Decimal（預設捨入）        不一致    503 / 200000 (0.3%)  886700分: 舊=13301 新=13300, 355100分: 舊=5327 新=5326
整數運算                 不一致      0 / 200000 (0.0%)
```

這個結果要這樣讀：

- 手選的典型案例**全部通過**。人類寫的、AI 寫的「典型案例」測試，都抓不到這個問題。
- 在 20 萬筆隨機輸入裡，兩種「看起來正確」的翻譯各有 503 筆差一分。原因是剛好落在「.5」的情況：舊系統的規則是遠離零（4.5 → 5），而 Python 的 `round` 與 `Decimal` 預設的捨入模式都是「四捨六入五成雙」（4.5 → 4，5.5 → 6）。
- 0.3% 看起來很小，但它是**系統性**的：每一筆落在平手情況的交易都錯，帳務對帳會永遠對不起來。
- 只有明確保留舊系統語意的版本（這裡是整數運算）全部一致。

**教訓：**語言移植最容易錯的是「兩邊都有、但預設行為不同」的東西：十進位與浮點、捨入模式、整數溢位、字串補齊與編碼、日期時區、排序與比較規則。AI 看得懂程式字面，但**不知道舊系統真正的語意是什麼**，除非你告訴它，或有人用差分測試把它逼出來。

## 移植的標準流程【判斷】

1. **把舊系統當 oracle**：從正式環境或預備環境匯出輸入與輸出樣本（注意去識別化），作為 golden master。
2. **以交易或程式為單位切片**：一次移植一個可獨立驗證的單元，而不是整個系統。
3. **差分測試要有「量」**：像上面的實驗，隨機加上邊界，數量要夠大，並且特別產生「平手」「溢位」「空值」「極端日期」這類輸入。
4. **平行執行（shadow mode）**：新舊系統同時吃正式流量，只用舊系統的結果，比對新系統的輸出，差異進入報表。
5. **逐步切換（strangler 模式）**：以路由逐步把流量轉到新系統，保留回退路徑。
6. **差異清單要有人負責**：每一種差異，要不是修正、就是明確記錄「可接受」並由業務方簽核。

## 把 AI 的「解釋」當成假設

用 AI 讀懂不熟的程式，是有用的（p.13–14），但解釋是**假設**，不是事實：

1. 要求它**引用行號或識別字**，每個說法都能對回原始碼。
2. 對關鍵說法寫一個**會失敗的測試**：如果解釋是對的，這個測試應該通過；如果它說「這裡會回傳 null」，就真的去呼叫看看。
3. 對沒文件的舊程式，先把解釋存成文件，**標示「AI 解釋，已驗證項目」與「未驗證項目」**，避免下一個人把假設當事實。
4. 對於語言標示、版本、方言（書中的例子是 Fortran 90/95 以上，p.14），可以拿編譯器或直譯器的版本資訊交叉確認。

## 檢查點

Q: AI 把一段 COBOL 的金額計算翻成 Java，團隊用 20 個手選的典型案例測試，全部通過。下一步最合理的是？
- [ ] 全部通過就代表翻譯正確，可以上線
- [ ] 增加到 200 個同類型的典型案例
- [x] 以舊系統為 oracle，用大量隨機與邊界輸入做差分測試，特別是捨入、平手、溢位等兩個平台預設行為可能不同的地方
- [ ] 請 AI 再審查一次自己的翻譯
解釋: 典型案例通過，只能證明典型情況沒問題。實驗裡 20 萬筆隨機輸入才暴露了 503 筆差異。讓同一個模型審查自己的輸出，也不能取代用舊系統當 oracle 的比對。

## 思考練習

Q: 公司有一套沒有文件的 COBOL 批次系統，管理層想用 AI 兩個月內「全部轉成 Java」。請提出你的風險評估與替代方案。
- 先指出風險：沒有 oracle 就沒有驗證；兩個月內無法涵蓋金額、日期、批次邊界等隱含語意。
- 提出分層策略：先用 AI 讀懂並建立文件與 characterization test，再用 strangler 逐段切換。
- 說明驗證：以舊系統為 oracle 的差分測試、平行執行、差異報表與簽核。
- 區分「忠實移植」與「重新設計」的目標，避免兩者混在同一個專案。
- 書中 DMV 專案花費 2.08 億美元後喊停，是時程與範圍失控的警示；用它爭取較合理的時程與里程碑。
