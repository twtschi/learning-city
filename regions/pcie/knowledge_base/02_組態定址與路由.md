# 組態、定址與路由

## 先後關係

PCIe 開機時不是「先有路由再找裝置」，而是：

1. Root 從已知的 Bus 0 開始探測。
2. Enumeration 指派 BDF 與 bridge bus numbers。
3. 軟體量測 BAR 需求並配置 MMIO/I/O 範圍。
4. 軟體把 bridge 的 Base/Limit window 設好。
5. 啟用 Memory Space、Bus Master、MSI/MSI-X、error reporting 等功能。
6. 之後 TLP 才能依地址或 ID 正確穿越 fabric。

〔BOOK p.144-175、180-225〕

## BDF：軟體看到的座標

BDF = Bus Number + Device Number + Function Number。

- Bus：8 bits，最多 256 個 bus number。
- Device：5 bits，每 bus 最多 32 個 device number；外部點對點 Link 的下游裝置通常固定為 Device 0。
- Function：傳統欄位 3 bits，每 device 最多 8 個 Function。
- 每個 Function 都有獨立 Configuration Space。

Switch 的 Port 對軟體呈現虛擬 PCI-to-PCI Bridge，因而建立新的 Bus 階層。〔BOOK p.144-145、214〕

## Configuration Space

| 區域 | 大小 | 存取方式 | 內容 |
|---|---:|---|---|
| PCI-Compatible Space | 256 bytes/Function | Legacy CF8/CFC 或 ECAM | 64-byte Header + capability list |
| Extended Configuration Space | 總計 4 KB/Function | ECAM | PCIe extended capabilities |

Type 0 Header 用於非 Bridge Function（常見為 Endpoint），有 6 個 BAR；Type 1 Header 用於 Bridge/Root Port/Switch Port，有 2 個 BAR 與 Primary/Secondary/Subordinate Bus Number、Base/Limit windows。PCIe Function 至少需要 PCI Express Capability，並支援 Power Management 及 MSI 和/或 MSI-X。〔BOOK p.147-148、185-186〕

### Configuration Request 的限制

只有 Root Complex 可產生 Configuration Request，且只能往下游走；Endpoint 不可任意改寫其他裝置。Configuration TLP 使用 ID Routing。〔BOOK p.150〕

### Type 0 與 Type 1 Configuration Request

- 目標 Bus 等於某 Bridge 的 Secondary Bus：往該 bus 送 Type 0，Device/Function 解碼並存取最終 Function。
- 目標 Bus 落在 Secondary..Subordinate 範圍但不等於 Secondary：以 Type 1 繼續往更深層 Bridge 傳遞。
- 到達最終 bus 時，Type 1 轉為 Type 0；這也是 ECRC 計算必須把 Type bit 的可變性排除在外的原因之一。

〔BOOK p.158-160、718〕

## Enumeration：深度優先探索

核心流程：

1. 從 Bus 0、Device 0、Function 0 開始讀 Vendor ID。
2. Vendor ID 有效代表 Function 存在；`FFFFh` 代表不存在。
3. 讀 Header Type 判斷 Endpoint（0）或 PCI-to-PCI Bridge（1）；multi-function bit 決定是否探測 Function 1-7。
4. 發現 Bridge 時，先暫設 Subordinate Bus Number = 255，指派新的 Secondary Bus Number。
5. 立即深入新的 bus，完成其下所有子樹後再回到上一層，最後收斂 Subordinate Bus Number。

這是 depth-first search。〔BOOK p.163-174〕

### 不存在與尚未就緒不可混為一談

- **Device absent**：下游 Bridge 回 Completion Status = UR；Root 為相容性向軟體呈現全 1，Vendor ID 即 `FFFFh`。
- **Device present but not ready**：Function 可回 CRS。Root 可重試，或在 CRS Software Visibility 啟用且讀 Vendor ID 時回人工值 `0001h`，讓軟體稍後再查。

Enumeration 期間的「探測不到」常是預期事件，不應直接當成一般 runtime error。〔BOOK p.164-166〕

## BAR：向軟體宣告地址需求

裝置不能自行決定系統位址；它用 BAR 表示所需空間的類型、大小與屬性，BIOS/OS 再配置基址。〔BOOK p.185-194〕

### 常見類型

- I/O BAR：僅為 legacy 相容，PCIe 不鼓勵新設計依賴 I/O space。
- 32-bit Memory BAR。
- 64-bit Memory BAR：佔用相鄰兩個 BAR dword。
- Prefetchable MMIO：讀取無副作用，允許預取/合併，有利效能。
- Non-Prefetchable MMIO：讀取可能有副作用，常用於控制/狀態暫存器。

### 量測與配置觀念

軟體會保存原值、寫入全 1、讀回硬體固定遮罩以推導 size/type，再寫入已配置的 base address。所有 BAR 都要逐一檢查；即使前一個未實作，也不能假設後面的都不存在。64-bit BAR 需把相鄰 BAR 當成一組。〔BOOK p.185-194〕

### Bridge Window

Endpoint 的 BAR 告訴它「哪些地址是我的」；Type 1 Header 的 Base/Limit window 告訴 Bridge「哪些地址位於我的下游」。Bridge 分別維護 Prefetchable MMIO、Non-Prefetchable MMIO、I/O 三類範圍。若任一上游 Bridge window 未涵蓋 Endpoint BAR，即使 Endpoint BAR 正確，Request 仍到不了裝置。〔BOOK p.195-203〕

## 三種 TLP 路由

| 路由方法 | 依據 | 典型 TLP |
|---|---|---|
| Address Routing | 32/64-bit Memory address 或 32-bit I/O address | Memory Read/Write、I/O Read/Write、AtomicOp |
| ID Routing | BDF | Configuration Request、Completion、部分 Message |
| Implicit Routing | 拓撲方向/既定目的地 | 多數 Message，例如往 Root 或廣播 |

〔BOOK p.204-224；BP p.6〕

### Address Routing

Endpoint 以 BAR 判斷是否接受；Switch/Bridge 以 BAR 與 Base/Limit window 判斷消耗、向下游轉發、向上游轉發或回報 Unsupported Request。Memory address < 4 GB 使用 3DW header；高於 4 GB 使用 4DW header。〔BOOK p.217-222〕

### ID Routing

使用 BDF 精準定位 Function。Configuration Request 往下游；Completion 依 Requester ID 返回；某些 Message 也可指定 ID。〔BOOK p.214-216〕

### Implicit Routing

僅適用 Message。它利用樹狀拓撲的上/下游方向與 Root 在頂端的事實，模擬被 PCIe 移除的 sideband signal 語意。〔BOOK p.222-224〕

## 快速診斷問題鏈

若驅動找得到裝置卻無法正常 MMIO，依序檢查：

1. BDF 與 Vendor/Device ID 是否穩定。
2. Header Type、BAR type/size/base 是否合理。
3. Command.Memory Space Enable 是否打開。
4. 每一層上游 Bridge 的 Base/Limit window 是否涵蓋該 BAR。
5. TLP address、3DW/4DW format、Byte Enable、Length 是否正確。
6. Completer 是否回 UR/CA，或 Requester 是否 Completion Timeout。
